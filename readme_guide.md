# 조별 README 작성 안내: 이론적 배경과 프롬프트 설계 정리하기

이 안내는 각 조가 README의 **이론적 배경**, **프롬프트 설계**, **시험 결과와 한계**를 쓰기 위한 것이다.

이론적 배경의 목적은 그럴듯해 보이는 포장이 아니다. 이미 정립된 용어로 각 조의 자료와 목적을 설명하여 제3자가 이해하기 쉽게 하고, 작업자 스스로도 더 넓은 관점에서 데이터를 다시 보기 위한 것이다. 프롬프트 설계와 시험 결과는 그 관점이 실제 챗봇에서 어떻게 구현되었고, 어디까지 구현되지 않았는지를 보여 준다.

작업 순서는 다음과 같다.

1. 조별 읽기 자료와 조의 작업물을 NotebookLM에 넣는다.
2. **큰 질문 세 가지**를 차례로 던지고, 답을 원문에서 확인한다.
3. 확인한 내용을 조원들의 말로 다시 써서 README에 넣는다.

---

## 1. 준비

1. https://notebooklm.google.com 에 접속하여 새 노트북을 만든다. 노트북 이름은 `조이름_README`로 한다.
2. 아래 **조별 읽기 자료**를 소스로 추가한다.
   - 웹 페이지는 주소를 그대로 넣는다(소스 추가 → 웹사이트).
   - 논문 PDF는 내려받은 뒤 파일로 올린다. 학술지 PDF 주소를 웹사이트로 넣으면 읽히지 않을 수 있다.
   - 유료 논문은 고려대학교 도서관을 통해 내려받는다. **내려받은 유료 논문 PDF는 GitHub 저장소에 올리지 않는다.**
3. 조의 작업물을 소스로 추가한다(소스 추가 → 복사한 텍스트). 소스마다 제목을 붙여 구분한다.
   - `딜레마와 선택지`: 조의 딜레마 한 줄과 선택지 목록(스프레드시트의 Dilemma, Option 행)
   - `프롬프트 1~4차`: 지난 시간 공유 시트에 적은 1차, 2차, 3차 프롬프트와 4차 구조화 프롬프트. 차수 표시를 지우지 않는다.
   - `실행 설정과 평가`: 공유 시트의 모델, temperature, 평가/소감
4. 강의자 저장소 README의 1장(이론적 배경)도 복사한 텍스트로 추가한다. 수업 전체의 관점과 조별 이론을 연결할 때 쓴다.

> API 키, Secrets 값은 어떤 소스에도 넣지 않는다.

## 3. 큰 질문 세 가지

질문은 한 번에 하나씩 던진다. 큰 질문을 먼저 던지고, 답이 막연하면 아래의 이어 묻기 문장을 차례로 쓴다. 모든 질문 끝에 다음 문장을 붙인다.

> 각 문장마다 근거가 된 소스를 표시해 줘. 소스에 없는 내용은 추측하지 말고 "소스에 없음"이라고 답해 줘.

### 질문 1. 용어: 이 자료들은 조가 다루는 현상을 무엇이라고 부르는가?

> 읽기 자료 소스에서 [조가 다루는 대상, 예: 인물이 공개 사과 대신 침묵을 택하는 상황]을 설명하는 데 쓸 수 있는 핵심 용어를 세 개 이내로 골라 줘. 각 용어의 원어, 자료에서의 정의, 그 정의가 나온 문장을 알려 줘.

이어 묻기
- 이 용어들 가운데 서로 비슷하거나 겹치는 것이 있다면 차이를 설명해 줘.
- 조원들이 평소에 쓰던 말 "[예: 이미지 관리]"는 이 자료의 어느 용어에 가장 가까워?

**얻어야 할 것:** 조가 README에서 일관되게 쓸 용어 2~3개와 그 정의.

### 질문 2. 분석 틀: 이 자료들은 그 현상을 어떤 기준으로 나누고 판단하는가?

> 읽기 자료 소스에서 질문 1의 용어들을 나누거나 판단하는 기준, 유형, 조건을 정리해 줘. 표로 만들되 각 항목에 근거 문장을 붙여 줘.

이어 묻기
- 이 기준을 `딜레마와 선택지` 소스의 딜레마, 선택지, 이유(사건·주장)에 대응시키면 어떻게 돼? 대응되지 않는 기준도 따로 알려 줘.
- 이 기준으로 보면 이 데이터셋의 선택지 중 빠진 것이 있어?

**얻어야 할 것:** 데이터셋의 클래스와 관계를 왜 그렇게 나누었는지 설명할 근거. 데이터를 보완할 거리가 나오면 따로 적어 둔다.

### 질문 3. 적용과 한계: 이 개념으로 조의 딜레마와 챗봇을 설명하면 어떻게 되고, 무엇이 설명되지 않는가?

> 이 데이터셋의 딜레마 "[주체]: ~할 것인가"와 `프롬프트 1~4차` 소스의 챗봇 설정을 질문 1, 2의 개념으로 설명해 줘. 그리고 이 개념으로 설명되지 않거나 맞지 않는 부분을 알려 줘.

이어 묻기
- `프롬프트 1~4차` 소스에서 차수마다 바뀐 규칙을 정리해 줘. 그 가운데 질문 1, 2의 개념으로 이유를 설명할 수 있는 것과 없는 것을 나눠 줘.
- 이 이론을 따를 때 챗봇이 해서는 안 되는 답은 무엇일까? 지금 프롬프트에 그 제약이 들어 있어? (예: 기록에 없는 실존 인물의 속마음을 단정하기, 사용자 대신 결정해 주기)
- `실행 설정과 평가` 소스의 평가 내용 가운데 데이터 보완으로 풀 문제와 프롬프트 수정으로 풀 문제를 나눠 줘.

**얻어야 할 것:** 조의 해석이 이론과 만나는 지점과 어긋나는 지점, 프롬프트 규칙 하나하나의 이유, 앞으로 고칠 거리.

## 4. NotebookLM 사용 규칙

1. **원문 확인:** 답변의 인용 번호를 눌러 원문 문장을 직접 읽는다. 원문에서 확인되지 않은 내용은 README에 쓰지 않는다.
2. **쪽수 기록:** README에 쓸 용어와 정의는 원문의 쪽수나 절을 함께 적어 둔다.
3. **그대로 옮기지 않기:** NotebookLM의 문장을 그대로 붙여 넣지 않는다. 확인한 내용을 조원들의 말로 다시 쓴다. 원문을 그대로 인용할 때는 따옴표와 쪽수를 붙인다.
4. **답이 이상할 때:** 자료에 없는 사람이나 이론이 나오면 그 답은 버리고 질문을 좁혀 다시 묻는다.
5. **프롬프트에 대한 판단은 조가 한다:** NotebookLM이 프롬프트 규칙의 이유를 설명해도, 실제로 그 규칙을 넣은 이유는 조원들이 기억하는 시험 과정과 대조해서 쓴다.
6. **기록 남기기:** 쓸모 있었던 답은 메모(노트에 저장)로 남겨 둔다. 다음 시간 교차 피드백에서 근거를 물을 때 쓴다.

## 5. README에 쓰는 방법

README v1 항목 가운데 아래 세 항목을 이 안내에 따라 채운다.

### 5.1 이론적 배경

세 문단으로 쓴다. 각 문단은 큰 질문 하나에 대응한다.

| 문단 | 담을 내용 | 문장 틀 |
|---|---|---|
| 1. 용어 | 조가 쓰는 핵심 용어와 정의 | "본 데이터셋은 ○○를 △△(저자 연도)의 개념인 '□□'로 이해한다. □□는 …을 뜻한다." |
| 2. 분석 틀 | 그 용어가 데이터 구조에 반영된 방식 | "△△는 □□를 ㉠, ㉡, ㉢으로 나눈다. 본 데이터셋은 이 구분을 선택지(Option)와 이유(Claim)로 기록하였다." |
| 3. 적용과 한계 | 조의 딜레마와 챗봇 설정에 적용한 결과, 설명되지 않는 부분 | "이 관점에서 ○○의 딜레마는 …으로 읽힌다. 다만 …은 이 개념으로 설명되지 않으므로, 챗봇은 …하지 않도록 설계하였다." |

**작성 예시: 강의자 README의 이론적 배경을 세 문단으로 줄인 것**

강의자 README 1장도 같은 세 질문에 답하는 방식으로 쓰였다. 아래는 그 내용을 조별 README 분량으로 줄인 예시이다. 각 조는 자기 데이터셋의 용어와 구조로 같은 형식을 채운다.

> **(용어)** 본 수업은 학생들이 고른 장면을 도덕적 딜레마(moral dilemma)로 이해한다. 도덕적 딜레마는 행위자에게 둘 이상의 행위가 각각 요구되고, 행위자가 각 행위를 할 수는 있으나 그 모두를 함께 할 수는 없는 상황을 말한다(McConnell 2022). 일상어의 딜레마가 난처한 상황 전반을 가리키는 것과 달리, 이 정의는 상충하는 요구 가운데 어느 것도 다른 요구를 무효로 만들지 못한다는 점에 초점을 둔다.
>
> **(분석 틀)** 이 정의의 조건은 공통 스키마로 옮겨졌다. 선택하는 행위자는 `dm:hasDecisionMaker`로, 각각 요구되는 행위는 둘 이상의 선택지(Option)로, 각 행위를 요구하는 근거는 `dm:isReasonFor`로 연결한 사건(Event)과 주장(Claim)으로 기록한다. 모두를 함께 할 수 없다는 조건 때문에, 실제로 일어나지 않은 선택지도 지우지 않고 데이터에 남긴다.
>
> **(적용과 한계)** 인물이 왜 그렇게 선택했는지는 텍스트가 모두 말해 주지 않으므로 작업자의 해석으로 채워진다(Iser 1976). 인문학의 데이터는 관찰자가 골라 구성한 것이라는 점에서(Drucker 2011), 이 데이터셋은 사실의 기록이 아니라 해석의 기록이다. 그래서 해석이 사실처럼 읽히지 않도록 확인된 사건과 누군가의 진술·해석을 사건과 주장으로 나누었다. 다만 챗봇은 데이터를 바탕으로 새 문장을 만들어 내므로, 이 구분이 응답에서도 지켜지는지는 대화를 시험하여 확인해야 한다.

세 문단은 각각 다음 내용에 답한다.
- **첫 문단:** 핵심 용어 하나와 그 정의, 출처.
- **둘째 문단:** 정의의 조건이 어떤 클래스와 관계로 바뀌었는지.
- **셋째 문단:** 이론이 데이터의 성격을 어떻게 규정하는지, 그리고 챗봇 단계에서 남는 한계.

### 5.2 프롬프트 설계

**(1) 프롬프트 변천표.** 1~4차 프롬프트 전문을 붙이지 않고, 차수마다 한 줄로 정리한다.

| 차수 | 바꾼 점 | 바꾼 이유 |
|---|---|---|
| 1차 | 처음 설정한 역할, 사용자, 핵심 규칙 | 기획 의도 |
| 2차 | 새로 넣거나 뺀 규칙 | 1차 대화 시험에서 발견한 문제 |
| 3차 | 새로 넣거나 뺀 규칙 | 2차 대화 시험에서 발견한 문제 |
| 4차 | 구조화 방식 | 어떤 LLM으로, 무엇을 기준으로 구조화했는지 |

- **바꾼 이유** 칸에는 "더 좋게 하려고" 같은 말 대신, 시험 대화에서 실제로 나온 문제를 쓴다. 예: 응답이 너무 길었다, 데이터에 없는 수치를 말했다, 사용자 대신 결론을 내렸다.

**(2) 최종 프롬프트의 구조.** 최종 프롬프트문은 저장소의 `prompt.txt`로 올리고, README에는 구조만 표로 설명한다.

| 구성 요소 | 내용 요약 | 넣은 이유 |
|---|---|---|
| 역할 | 챗봇이 누구이며 사용자는 누구인가 | |
| 맥락 | 시점, 장소, 챗봇이 아는 것과 모르는 것 | |
| 지식 범위 | 데이터만 쓰는가, 데이터 밖 배경 설명을 허용하는가 | |
| 응답 규칙 | 질문 유형별 대응 | |
| 제약 | 하지 않을 것 | |
| 출력 형식 | 말투, 길이, 호칭 | |
| 예시 대화 | (있다면) | |

**넣은 이유** 칸은 이론적 배경과 이어지게 쓴다. 특히 다음 두 가지는 이유를 반드시 밝힌다.
- **프롬프트에만 있는 설정:** 데이터가 아니라 프롬프트에서 주어진 인물의 성격이나 평가는 조의 해석이다. 그 근거를 적는다.
- **실존 인물 관련 제약:** 실존 인물을 연기하거나 실존 인물이 등장하면, 기록에 없는 말을 지어내지 않도록 둔 제약과 사용자에게 보여 주는 안내문을 적는다.

**(3) 실행 설정.** 모델과 temperature를 적고, 그 값을 고른 이유를 한 문장으로 쓴다. 설정을 바꿔 가며 시험했다면 최종값이 무엇인지 분명히 적는다.

### 5.3 시험 결과와 한계

| 항목 | 쓸 내용 |
|---|---|
| 시험한 질문 | 실제로 던진 대표 질문 3~5개 |
| 의도대로 된 것 | 규칙대로 답한 사례 |
| 의도대로 되지 않은 것 | 규칙을 어기거나 데이터 밖으로 나간 사례 |
| 보완 계획 | 데이터로 보완할 것과 프롬프트로 보완할 것을 나누어 적는다 |

공유 시트의 평가/소감은 이 항목의 초안이다. 질문 3의 마지막 이어 묻기로 데이터 문제와 프롬프트 문제를 나눈 결과를 여기에 옮긴다.

### 5.4 참고문헌과 AI 사용 표기

- 참고문헌에는 실제로 읽고 확인한 자료만 원문 링크와 함께 적는다.
- AI 사용 표기에는 다음을 모두 적는다.
  - 4차 프롬프트 구조화에 쓴 LLM과 그 범위. 예: "4차 프롬프트는 1~3차 프롬프트와 대화 시험 결과를 ○○에 제공하여 구조화하였으며, 조원이 검토·수정하였다."
  - 이론적 배경 요약에 NotebookLM을 쓴 사실. 예: "이론적 배경의 자료 요약에 Google NotebookLM을 사용하였으며, 요약 내용은 조원이 원문과 대조하여 다시 썼다."
  - app.py 변형 등 그 밖에 AI를 쓴 작업.

## 6. 제출 전 점검

**이론적 배경**
- [ ] 핵심 용어 2~3개에 정의와 출처(쪽수 또는 절)가 붙어 있다.
- [ ] 각 용어가 데이터셋의 어느 클래스나 관계와 이어지는지 썼다.
- [ ] 이론으로 설명되지 않는 부분을 한 가지 이상 썼다.

**프롬프트 설계, 시험 결과**
- [ ] 1~4차 변천표의 "바꾼 이유"가 실제 시험에서 발견한 문제로 적혀 있다.
- [ ] 최종 프롬프트문이 `prompt.txt`로 저장소에 올라가 있다.
- [ ] 프롬프트에만 있는 인물 설정과 실존 인물 관련 제약의 이유를 밝혔다.
- [ ] 모델과 temperature의 최종값이 하나로 적혀 있다.

**공통**
- [ ] NotebookLM의 문장을 그대로 붙여 넣은 곳이 없다.
- [ ] 참고문헌에 원문 링크가 있고, 유료 논문 PDF를 저장소에 올리지 않았다.
- [ ] AI 사용 표기에 4차 구조화 도구와 NotebookLM 사용을 적었다.
