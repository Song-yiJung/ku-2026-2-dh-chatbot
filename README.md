## 1. 딜레마: 수업과 데이터의 이론적 배경

### 1.1 수업의 문제의식

대학 졸업을 앞둔 학부생은 스스로 진로를 선택해야 하는 시점에 서 있으며, 그 과정은 연속된 딜레마로 이루어진다. 특히 생성형 인공지능의 등장으로 여러 산업 환경이 빠르게 바뀌면서, 학생들은 인공지능이 일자리를 줄이리라는 불안을 직접 경험하기보다 미디어를 통해 먼저 접하고 있다. 본 수업은 학생들이 자신의 관심사인 콘텐츠에서 딜레마의 순간을 골라 능동적 독자로서 읽고, 생성형 인공지능을 도구로 삼아 그 순간을 데이터와 챗봇으로 구현하도록 하였다. 이 과정에서 학생들은 딜레마를 판단하는 자신의 기준을 세우고, 생성형 인공지능이 무엇을 할 수 있고 무엇을 할 수 없는지를 직접 확인한다.

### 1.2 딜레마의 개념

딜레마(dilemma)는 고대 그리스어 디렘마(δίλημμα)에서 온 말로, '둘'을 뜻하는 디(di-)와 '전제' 또는 '취해진 것'을 뜻하는 레마(lēmma)가 결합한 것이다. 수사학과 논리학에서 이 말은 상대에게 두 전제를 제시하고, 어느 쪽을 받아들여도 불리한 결론에 이르게 하는 논증 형식을 가리켰다. 일상 언어에서는 이 뜻이 넓어져 해결하기 어려운 곤경이나 난제 전반을 가리키게 되었다.

본 수업이 데이터 모델링과 챗봇 구현의 주제로 삼은 것은 1960년대 레몬(E. J. Lemmon)과 윌리엄스(Bernard Williams)가 정식화한 도덕적 딜레마이다(Lemmon 1962; Williams 1965). 그 이전의 도덕 이론은 의무 사이의 충돌을 대개 외견상의 충돌로 보았다. 충돌하는 의무 가운데 하나가 다른 것보다 우선하면 충돌은 해소된다고 보았기 때문이다. 이와 달리 도덕적 딜레마는 다음 조건을 갖춘 상황이다. 행위자에게는 둘 이상의 행위가 각각 요구되고, 행위자는 각 행위를 할 수 있으나, 그 모두를 함께 할 수는 없다(McConnell 2022). 상충하는 요구 가운데 어느 것도 다른 요구를 압도하거나 무효로 만들지 못하므로, 행위자는 어느 쪽을 택하더라도 지키지 못한 요구를 남기게 된다.

도덕 이론의 오랜 목표는 인간에게 명확하고 유일한 행위 지침을 주는 데 있었다. 그러나 생명윤리와 법윤리 같은 응용윤리가 발전하면서, 일반적인 도덕 의무끼리 충돌하거나 공공의 이익을 위해 도덕적 악을 감수해야 하는 현실의 가치 갈등을 체계적으로 다루는 일이 중요한 과제가 되었다. 도덕적 딜레마에 대한 논의는 선택 이후 행위자에게 남는 죄책감이나 가책, 곧 도덕적 잔여(moral residue)가 진정한 도덕적 실패의 증거인지 단순한 유감인지를 묻는다. 또한 오랫동안 타당하다고 여겨 온 원칙들이 서로 모순될 때 무엇을 고치거나 내려놓아야 하는지를 따지게 한다. 이러한 물음은 행위자가 실제 선택 앞에서 자신의 판단 기준을 분명히 하도록 돕는다.

### 1.3 딜레마에서 데이터로

본 수업의 데이터 스키마는 위의 정의를 그대로 구조로 옮겼다. 딜레마(Dilemma)마다 선택하는 행위자 한 명을 두고, 그가 고를 수 있었던 둘 이상의 선택지(Option)를 연결한다. 선택지에는 실제로 일어나지 않은 길도 포함한다. 각 선택지를 요구하는 이유는 사건(Event)이나 주장(Claim)으로 연결한다.

이때 작업자인 학생은 자료의 첫 번째 독자이다. 텍스트는 모든 것을 설명하지 않으며, 독자는 비워진 자리를 채우며 읽는다(Iser 1976). 인물이 왜 그렇게 선택했는지, 그때 무엇을 알았고 무엇을 몰랐는지는 작업자의 해석으로 정해진다. 인문학의 데이터는 주어진 것이 아니라 관찰자가 골라 구성한 것이라는 점에서(Drucker 2011), 본 수업의 데이터셋은 작업자의 해석을 담은 기록이다. 다만 해석이 사실처럼 읽히지 않도록, 확인된 사건과 누군가의 진술·의심·해석을 사건(Event)과 주장(Claim)으로 나누어 기록하였다.

### 1.4 수업 방법론

본 수업의 방법론은 두 갈래의 선행 논의에 바탕을 둔다. 하나는 텍스트를 데이터로 구조화하며 읽는 디지털 인문학의 읽기 교육이고, 다른 하나는 디지털 매체에서 다른 독자와 감상을 나누며 읽는 디지털 소셜 리딩(digital social reading)이다.

#### 1.4.1 데이터 기반 읽기 교육

류인태는 『논어』를 대상으로 한 디지털 인문학 강의에서, 학생들이 고전 텍스트를 데이터로 설계하고 구축하고 해석하는 과정 자체를 읽기의 방법으로 삼았다(류인태 2021). 설계 단계에서 학생들은 탐구 주제를 클래스, 개체, 속성, 관계의 체계로 나누어 온톨로지를 만든다. 구축 단계에서는 공유 스프레드시트에서 팀 단위로 원자료를 수집·편찬한다. 정동이나 감정의 범주를 정하고 해당 구절을 고르는 일에는 작업자 개인의 판단이 개입하기 쉬우므로, 팀원 네 명 가운데 세 명 이상이 동의한 항목만 최종 데이터로 채택하는 교차 검토 방식을 두었다. 구축한 데이터는 수강생 전체에 공개되어, 다른 팀의 데이터를 자신의 탐구 주제와 결합하는 개인 과제로 이어졌다. 해석 단계에서 학생들은 그래프 데이터베이스인 Neo4j를 직접 설치하고 질의어인 Cypher를 익혀 데이터에 질의하고, 그 결과로 나온 노드와 관계의 시각화를 정성적·정량적으로 분석하여 새로운 해석을 제안한다. 류인태는 이를 사람과 책 사이에 컴퓨터라는 매개자를 두고 대화하는 읽기로 보았다. 이 과정에서 학생은 주어진 해설을 받아들이는 독자에서 지식의 구조를 설계하는 독자로 바뀐다.

본 수업은 이 세 단계를 따르되, 대상을 고전에서 학생들의 관심사인 작품, 인물, 사건으로 넓혔다. 학생들은 공통 딜레마 스키마에 따라 각자의 자료를 온톨로지 기반의 시맨틱 데이터로 구성하고, 공유 스프레드시트에서 팀 단위로 원자료를 편찬하며, 다른 팀과 교차 피드백을 주고받는다.

#### 1.4.2 디지털 소셜 리딩

피안졸라(Pianzola)는 디지털 소셜 리딩을 컴퓨터, 태블릿, 휴대전화, 전자책 단말기 같은 디지털 기술과 웹사이트, 소셜 미디어, 모바일 앱 같은 플랫폼을 이용해 이야기와 여러 문서에 대한 생각과 인상을 나누는 읽기 실천 전반을 포괄하는 용어로 규정하였다(Pianzola 2024, 11). 그는 디지털 매체와 기술이 문학 읽기의 즐거움과 이해를 높일 잠재력을 분석하는 것을 저서의 목적으로 삼았으며(Pianzola 2024, 2–3), 읽기의 사회적 차원이 텍스트 이해와 학습에 차이를 만들 수 있다는 연구 결과에 주목하였다(Pianzola 2024, 30). 또한 다른 독자의 주석과 댓글이 어려운 구절을 풀어 읽게 돕고, 정서를 조절하고 맥락을 파악하는 데 기여할 수 있다고 보았다(Pianzola 2024, 165–167, 172–176). 디지털 소셜 리딩에서는 정서적 공감과 자발적인 감상 공유가 읽기를 이끄는 동기로 작동하며, 읽기는 주석, 리뷰, 2차 창작과 같은 쓰기와 결합한다.

#### 1.4.3 두 접근의 결합과 챗봇의 자리

두 접근은 디지털 매체를 매개로 읽기를 혼자 하는 사적 행위에서 함께하는 활동으로 넓히고, 읽기를 쓰기 또는 생성과 결합한다는 점에서 공통된다. 그러나 데이터 기반 읽기 교육이 형식화된 데이터 구조와 학술적 엄밀성을 특징으로 한다면, 디지털 소셜 리딩은 비정형의 주석과 정서적·자발적 동기를 특징으로 한다. 본 수업은 데이터의 구조를 앞의 것에서, 함께 읽기의 동기를 뒤의 것에서 가져와 결합하였다.

| | 데이터 기반 읽기 교육(류인태) | 디지털 소셜 리딩(Pianzola) | 본 수업 |
|---|---|---|---|
| 읽기의 맥락 | 대학 강의(프로젝트 기반 학습) | 여가 독서, 온라인 독서 공동체 | 대학 강의(프로젝트 기반 학습) |
| 대상 | 고전(『논어』) | 소설, 웹소설, 팬픽션 등 | 학생이 고른 작품, 인물, 사건 |
| 읽기의 산출물 | 온톨로지, 지식그래프 | 댓글, 주석, 리뷰, 2차 창작 | 딜레마 데이터셋과 챗봇 |
| 데이터와의 상호작용 | Neo4j 데이터베이스에 대한 Cypher 질의 | (구조화된 데이터 없음) | 챗봇과의 자연어 대화 |
| 함께 읽기의 방식 | 교차 검토(4인 중 3인 동의), 다른 팀 데이터의 활용 | 감상과 주석의 공유 | 팀 간 교차 피드백, 다른 수강생과 챗봇의 대화 |
| 읽기의 동기 | 학술적 탐구 | 정서적 공감, 자발적 공유 | 관심 대상의 선택과 학술적 구조화 |

챗봇은 두 접근을 잇는 자리에 놓인다. 류인태의 수업에서 학생은 Cypher 질의로 데이터와 대화하였으나, 본 수업에서 학생은 자신의 데이터를 바탕으로 한 챗봇과 자연어로 대화한다. 질의어는 데이터에 있는 것만 돌려주지만 챗봇은 데이터를 바탕으로 새로운 문장을 만들어 낸다. 따라서 학생은 챗봇의 응답이 자신의 데이터와 해석을 어디까지 반영하고 어디서 벗어나는지를 확인해야 하며, 이 확인 과정에서 생성형 인공지능이 할 수 있는 것과 할 수 없는 것을 직접 경험한다. 나아가 다른 수강생이 그 챗봇과 대화하고 질문을 던지는 과정은 작업자의 해석을 다른 독자와 나누는 또 하나의 함께 읽기가 된다. 피안졸라의 논의가 사람 독자들 사이의 함께 읽기를 다룬다는 점에서, 챗봇을 매개로 한 함께 읽기는 본 수업이 그의 논의를 확장한 것이다. 데이터의 소재를 학생의 관심사에 열어 둔 것 역시, 디지털 소셜 리딩에서 확인되는 자발적 공유의 정서적 동기가 학습에서도 작동하도록 하기 위함이다.

## 2. 공통 딜레마 스키마

모든 조는 아래의 공통 클래스와 관계를 함께 쓰고, 자료에 따라 조별 관계를 덧붙인다.

**딜레마의 정의:** 둘 다 지킬 이유가 있지만 둘 다 가질 수는 없는 선택의 국면. 이름은 "[주체]: ~할 것인가"의 형식으로 붙인다.

| 구분 | 클래스 |
|---|---|
| 딜레마의 핵심 | Dilemma(딜레마), Option(선택지, 실현되지 않은 길 포함) |
| 행위자와 배경 | Person, Organization, Place, Object, Work |
| 시간과 서사 | Event, Episode, Scene |
| 말과 기록 | Utterance, Document, Claim, Concept |

| 관계 | 뜻 |
|---|---|
| dm:hasDecisionMaker | 딜레마의 선택 주체 |
| dm:hasOption | 딜레마가 가진 선택지 |
| dm:actualChooser | 그 선택지를 실제로 고른 사람 (Option에만) |
| dm:isRealizedBy / dm:isOutcomeOf | 선택지가 실현된 사건 / 선택의 결과 |
| dm:isReasonFor | 어떤 사건이나 주장이 선택의 이유가 됨 |
| dm:hasClaimant / dm:isAbout / dm:isEvidenceFor | 주장의 화자 / 주장의 대상 / 주장의 근거 |
| dm:precedes / dm:hasCause / dm:leadsTo | 사건의 순서와 인과 |

전체 관계 목록과 조별 관계(md:, bss:, for:, anr:, oakebo:)는 수업 스키마 시트를 따른다. 시험용 예시 데이터는 판소리 〈흥보가〉로 만든 `sample_data.ttl`이다.

## 5. 실습 틀 사용법

### 5.1 파일 구성

| 파일 | 내용 | 조에서 |
|---|---|---|
| team_config.py | 챗봇 이름, 모델, temperature, 전시 모드 등 설정 | 채운다 |
| prompt.txt | 프롬프트문 | 채운다 |
| data.ttl | 데이터셋 (여러 개면 data로 시작하는 .ttl 파일) | 올린다 |
| greeting.txt | 대화를 시작할 때 챗봇이 먼저 건네는 말 | 필요하면 채운다 |
| questions.txt | 추천 질문 (한 줄에 하나, 6개 이하) | 필요하면 채운다 |
| notice.txt | 전시 모드에서 화면 위에 띄울 고지문 | 전시 때 채운다 |
| app.py | 앱 화면 | 열지 않아도 됨 (화면을 더 바꾸고 싶을 때만) |
| engine.py | Gemini API 호출 | 수정 금지 |
| ttl_to_text.py | ttl을 문장형 텍스트로 바꾸는 모듈 | 수정 금지 |
| requirements.txt | 설치 목록 | 수정 금지 |
| sample_prompt.txt, sample_data.ttl | 시험용 예시(흥보가) | 참고용 |

텍스트 파일이 없거나 비어 있으면 그 기능은 쓰지 않는다. **API 키는 어떤 파일에도 적지 않는다.**

### 5.2 조별 챗봇 만들기

1. 강의자 저장소의 파일을 모두 내려받아, 각 조의 저장소에 올린다.
2. `team_config.py`를 열어 따옴표 안의 값과 숫자만 바꾼다.
3. `prompt.txt`에 프롬프트문을 붙여 넣고, 데이터셋을 `data.ttl`이라는 이름으로 올린다.
4. 필요하면 `greeting.txt`, `questions.txt`에 첫 인사와 추천 질문을 쓴다.
5. 조의 저장소를 Streamlit에 배포한다. (아래 "배포" 참고)
6. 앱 화면 위쪽의 **"우리 조 설정 확인"**을 열어, 파일과 설정을 제대로 불러왔는지 확인한다. 잘못된 곳이 있으면 이 칸에 한국어로 표시된다.

실습 모드에서는 저장소의 `prompt.txt`와 `data.ttl`이 자동으로 들어가 있다. 화면에서 프롬프트문을 고치거나 다른 파일을 올려 시험할 수 있으며, 이렇게 고친 내용은 저장소 파일을 바꾸지 않는다. 마음에 드는 결과가 나오면 그 내용을 저장소의 파일에 반영한다.

### 5.3 강의자가 실습 틀을 고쳤을 때

`app.py`, `engine.py`, `ttl_to_text.py`만 새 파일로 바꿔 올리면 된다. 각 조가 채운 `team_config.py`와 텍스트 파일은 그대로 둔다. (`app.py`를 직접 변형한 조는 바꾼 부분을 새 파일에 다시 옮겨야 한다.)

### 5.4 화면을 더 바꾸고 싶을 때 (선택)

대화 상대 선택 버튼, 딜레마 선택 버튼처럼 화면 구성을 바꾸려면 `app.py`의 ✏️ 표시 부분을 고친다. 각자 쓰는 LLM(ChatGPT, Claude, Gemini 등)에 `app.py`를 붙여 넣고 수정을 요청해도 된다. 코드 맨 위 주석에 수정 범위가 적혀 있어서 LLM이 그 범위를 따른다.

- 요청 예: "이 app.py를 ○○ 챗봇 컨셉에 맞게 바꿔 줘. 파일 맨 위 주석의 수정 범위를 지켜 줘."

AI를 써서 변형했다면 `team_config.py`의 `AI_USE_NOTE`에 어떤 도구로 무엇을 바꿨는지 적는다.

### 5.5 배포 (Streamlit Community Cloud)

share.streamlit.io → New app → 조의 저장소 선택, Main file path에 `app.py` 입력 → Deploy. 나온 주소로 접속한다.

### 5.6 전시 모드 (학회·시연용)

참여자가 링크만 눌러 바로 대화할 수 있는 화면이다.

- 저장소의 `prompt.txt`, `data.ttl`, `greeting.txt`, `questions.txt`, `notice.txt`를 그대로 쓴다.
- 모델과 temperature는 `team_config.py`의 값으로 고정된다.
- API 키·모델·파일 업로드 칸, 지시문 미리보기, 대화 기록 내려받기는 보이지 않는다.
- 다음 참여자를 위한 "새 대화 시작" 버튼이 나타난다.
- 동시 접속이 몰리면 참여자용 안내 문구가 한국어와 영어로 나타난다.

**전시 모드 켜기 (키를 관리하는 사람이 할 일)**

앱 설정 → Secrets에 아래 두 줄을 넣는다.

```toml
GEMINI_API_KEY = "행사용 키"
EXHIBIT_MODE = true
```

- Secrets의 `EXHIBIT_MODE`를 지우면 같은 주소가 다시 실습 화면으로 돌아간다. (`team_config.py`에서 `EXHIBIT_MODE = True`로 바꿔도 전시 모드가 켜진다.)
- 파일이나 키가 빠져 있으면 화면에 "[관리자 확인 필요]" 안내가 나타난다.
- 행사가 끝나면 키를 Secrets에서 지우고, 발급처에서도 키를 삭제한다.

> **주의:** 전시 모드의 앱 주소를 아는 사람은 누구나 행사용 키로 호출할 수 있다. 행사 전용 키를 따로 발급하고, 행사가 끝나면 바로 삭제한다.

### 5.7 내 컴퓨터에서 실행

```bash
pip install -r requirements.txt
streamlit run app.py
```
